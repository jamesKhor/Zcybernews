## Executive Summary

Eight intermediate certificate authority private keys belonging to Indian CA eMudhra Limited were generated with insufficient randomness, a cryptographic defect that allows third parties to derive the private keys directly from the public certificates. Unit 42, which published the analysis on October 22, 2026, said the weakness permits unauthorized signing of public TLS certificates and meddler-in-the-middle (MitM) interception, impersonation, or session hijacking against targeted domains. eMudhra has revoked the eight intermediates, and major browser and operating system vendors have moved to revoke or untrust them.

The practical consequence for defenders is that any certificate chaining to those intermediates can no longer be treated as trustworthy, and any trust store that still anchors them is a liability. The flaw is not an exploit against a specific product version but a failure in the key-generation process itself, which means the exposure is bounded by where those certificates were trusted rather than by a patchable software bug.

## Technical Analysis

According to Unit 42, the root cause is a critical cryptographic defect during certificate generation: the private keys were produced with insufficient randomness. When a key pair is generated with weak entropy, the private key can be recovered from the public key or certificate by an attacker, collapsing the security assumption that underpins the entire chain of trust. Unit 42 states that this allows a third party to derive the private keys, sign unauthorized public TLS certificates, and conduct MitM traffic interception, impersonation, or session hijacking against targeted domains.

The affected material is eight intermediate CA certificates issued under eMudhra. An intermediate CA sits between a trusted root and the leaf certificates presented by servers, so compromise of an intermediate key lets an attacker mint leaf certificates that validate against the root without ever touching the root key. Because the derivation is possible from public data, an attacker does not need to breach eMudhra infrastructure to obtain the keys — the certificates themselves are the starting point.

Unit 42 attributes the containment to eMudhra, which revoked the eight certificates, and to browser and OS vendors, which have moved to revoke or untrust the intermediates. The publication does not name the specific browser or OS versions that shipped the distrust, and it does not provide a timeline for when the weak keys were generated or how long they were in circulation. Those details are absent from the source and should not be assumed.

The source does not identify a threat actor, does not attribute any observed MitM campaign to the compromise, and provides no indicators of compromise such as hashes, IP addresses, or domains. Unit 42 frames the risk as potential rather than confirmed exploitation.

## Mitigations & Recommendations

Unit 42's interim guidance centers on discovering where the compromised intermediates are trusted and removing that trust. The first step is to inventory public-facing services, web applications, API endpoints, VPN gateways, and internal infrastructure, and identify any active TLS certificate that chains up to an eMudhra intermediate. The same audit should extend to code repositories and build pipelines, checking whether eMudhra intermediates or hard-coded trust anchors were bundled into applications, API clients, containers, or custom runtime environments.

Internal trust stores need separate scrutiny. Unit 42 recommends searching for eMudhra roots or intermediates inside custom enterprise stores, naming Linux `/etc/ssl/certs`, Java keystores, Python `certifi` bundles, Docker base images, and mobile application bundles as places where stale anchors persist.

For containment, any certificate issued under the compromised intermediates should be revoked and reissued through an alternative, fully trusted CA. Updated root and intermediate trust stores should be pushed via mobile device management across endpoints, servers, and container images to explicitly distrust or revoke the affected eMudhra intermediates. Enterprise web proxies, API gateways, outbound egress controls, and security appliances should enforce strict CRL and OCSP checking so connections presenting revoked chains are blocked.

For hunting, Unit 42 advises searching network, proxy, and DNS logs for connections to unknown external IPs using eMudhra-signed certificates, and watching for unexplained spikes in TLS handshake failures, certificate validation errors, or untrusted issuer warnings that could indicate active MitM or proxy insertion. Authentication logs for SSO, VPN, and cloud portals should be reviewed around the compromise window for signs that sessions were intercepted or replayed.

Longer-term, Unit 42 recommends monitoring Certificate Transparency logs such as crt.sh for unauthorized certificates issued for the organization's domains, enforcing DNS CAA records to restrict which CAs may issue for those domains, and moving to automated certificate lifecycle management with short-lived certificates to shrink the impact window of future CA key compromises.
